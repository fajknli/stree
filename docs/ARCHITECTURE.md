# stree 架构哲学与内核设计

> 本文档记录 `stree` 引擎的核心设计决策、架构约束，以及每一个关键技术选择背后的工程推演。面向源码阅读者、贡献者，以及所有对 TUI 引擎底层机制感兴趣的人。

---

## 1. 范式声明：为什么不是另一个 TUI 框架

### 1.1 拒绝 Retained Mode

主流 TUI 框架（Ratatui、Bubble Tea、tview）采用 **Retained Mode**：开发者在代码中构建组件树，框架持有状态，每一帧进行 diff 和重绘。这种模式适合构建"应用"，但不适合构建"底座"。

`stree` 的选择是 **Immediate Mode + 外部状态**：
*   引擎不持有任何业务状态。
*   每一帧，引擎从内存中的 Dataset 纯函数式地投影出屏幕画面。
*   状态的演化由外部脚本通过 stdin/IPC 驱动。

这意味着 `stree` 本质上是一个**渲染器**，而非**应用框架**。它的职责边界极其清晰：接收数据，画出界面，转发意图。

### 1.2 为什么纯 Rust 手写，不依赖 TUI 库

`stree` 的渲染层直接基于 `crossterm` 的原语（`MoveTo`、`Print`、`SetForegroundColor`），没有使用任何高级 TUI 组件库。原因有三：

1.  **像素级控制**：TUI 的布局精度要求极高。一个字符的溢出就会导致终端换行，换行会导致布局坍塌。使用高级框架意味着放弃对每一列、每一行的绝对控制权。
2.  **零抽象成本**：`stree` 的渲染循环是单线程同步的，没有任何异步运行时开销。每一帧的渲染路径是确定的、可预测的。
3.  **ANSI 透传**：引擎需要完美地透传外部命令输出的 ANSI 转义序列，同时精准计算可见字符宽度。这要求渲染器必须理解 ANSI 的内部结构，而不是把它当作黑盒字符串。

## 2. 协议驱动：Unix 管道哲学的极端化

### 2.1 四列 TSV 协议的设计动机

为什么是 4 列？为什么是 TSV？

*   **TSV（制表符分隔）**：制表符在自然文本中几乎不会出现，因此不需要转义机制。相比 CSV，TSV 的解析成本低一个数量级，且完美兼容 `awk`、`cut`、`sort` 等 Unix 标准工具。
*   **4 列的最小完备性**：
    *   第 1 列（ID）：图论必需的主键。
    *   第 2 列（Display）：人类可读的展示文本。
    *   第 3 列（Path）：机器可操作的业务负载。
    *   第 4 列（Tags）：多维度分类与样式映射的统一载体。

少于 4 列无法表达完整的树形交互语义；多于 4 列则意味着引擎开始理解业务语义，违背了"零业务侵入"原则。

### 2.2 Display 与 Path 的正交分离

这是协议设计中最关键的正交性决策。

*   `Display` 是给人看的。它可以包含 `[tag]`、`(type)` 等格式化信息，甚至包含 ANSI 颜色码。引擎只负责渲染，不解析。
*   `Path` 是给机器用的。它是外部命令的参数，是 `vim {path}` 中的 `{path}`。引擎绝不打开它、读取它或解释它。

这种分离确保了业务层可以自由地组合展示文本（例如 `title " (" type ")"`），而不影响命令执行的准确性。

### 2.3 第四列的演化：从 Status 到 Tags

在早期设计中，第四列名为 `status`，是一个单一值（如 `live` 或 `archived`）。

问题很快浮现：业务层需要同时表达"这是一个 note 类型的文件"和"这个文件已被归档"。如果只有一个字段，业务层要么拼接成 `archived_note`（导致样式规则爆炸），要么被迫添加第五列（破坏协议稳定性）。

**最终方案：标签集（Tag-Set）**。
第四列改为逗号分隔的标签集（如 `archived,note,inbox`），样式引擎从"全等匹配"升级为"包含匹配"。这一改动在不改变协议物理结构（依然是 4 列 TSV）的前提下，将表达能力从一维提升到了 N 维。

## 3. 执行模型：双轨制与死锁防御

### 3.1 为什么需要双轨制

TUI 引擎面临一个根本矛盾：**终端只有一个，但引擎和外部命令都想拥有它。**

*   当用户按 Enter 打开 `vim` 时，`vim` 必须拥有终端的控制权（Raw Mode、Alternate Screen、TTY 的 stdin/stdout）。引擎必须完全让出。
*   当用户按 Ctrl-T 切换视图时，业务脚本只需要修改一个状态文件并触发刷新。它不需要终端的控制权，引擎不应该让出。

如果用同一种模式处理这两种场景，要么 `vim` 无法正常运行（因为引擎没有让出 TTY），要么视图切换时会黑屏闪烁（因为引擎不必要地让出了 TTY）。

**双轨制执行模型**因此诞生：
*   **默认模式**：让出一切。适用于全屏交互工具。
*   **`@` 静默模式**：保留一切。适用于纯后台状态变更。

### 3.2 `@` 模式下的 fd 继承死锁

这是 `stree` 开发过程中发现的最危险的系统级陷阱。

**陷阱的触发路径**：
1.  用户绑定 `--bind "ctrl-l=@sh -c 'long_task &'"`
2.  `stree` fork 出 `sh` 进程。如果使用 `.output()`，Rust 会创建 pipe 连接子进程的 stdout/stderr。
3.  `sh` 执行 `long_task &`，`long_task` 作为孙进程，**默认继承 `sh` 的 stderr pipe 写端**。
4.  `sh` 瞬间退出。但 `long_task` 仍持有 pipe 写端。
5.  Rust 的 `.output()` 阻塞在 `read(pipe)` 上等待 EOF。由于 `long_task` 未关闭写端，EOF 永远不会到来。
6.  `stree` 主线程死锁。TUI 完全无响应。

**防御方案**：
在静默模式下，将 stdin、stdout、stderr **全部重定向到 `/dev/null`**，并使用 `.status()` 替代 `.output()`。`.status()` 只调用 `waitpid()`，不读取任何管道。即使后台任务继承了 fd，也不会影响主线程。

**代价**：静默模式下无法捕获 stderr 错误信息。但这是完全可接受的权衡——UI 的绝对流畅性优先于错误文本的展示。退出码依然可用，业务层可通过 IPC 推送详细的错误信息。

### 3.3 IPC 死锁的另一面

当 `@` 模式的业务脚本内部调用 `stree update`（IPC 推送）时，如果 IPC 调用是同步的，会形成另一种死锁：
*   `stree` 主线程阻塞在等待脚本退出。
*   脚本阻塞在等待 `stree` 处理 IPC 请求。

**解决方案**：业务层必须将 IPC 调用放入后台（`(...) &`），让脚本瞬间退出。引擎在下一轮主循环的 poll 中处理 IPC 请求。这不是引擎的缺陷，而是同步架构下正确的协作契约。

## 4. 局部刷新：从全量重绘到定向 IPC

### 4.1 全量重绘的代价

在早期设计中，任何外部命令执行完毕后，引擎会重新执行所有 `--tree` 的数据源命令，重建整个 Dataset，然后清空屏幕重新渲染。

对于 `brain-tui` 这样的知识库系统，这意味着：
*   每次切换视图，都要重新读取数百个 Markdown 文件的 frontmatter。
*   每次归档一个文件，都要重建整棵树。
*   屏幕会短暂闪烁（即使使用了 Alternate Screen，清空重绘依然有视觉抖动）。

### 4.2 IPC 定向刷新机制

`stree update <window_name>` 的引入，将刷新粒度从"全局"降维到了"组件级"。

*   **Tree 组件**：接收新的 TSV 流，增量更新 Dataset，保留展开/选中状态，仅重绘该树窗口。
*   **View 组件**：直接替换内容缓冲区，仅重绘该预览窗口。
*   **StatusBar 组件**：直接替换文本，仅重绘状态栏。

其他组件完全不受影响。这种"指哪打哪"的刷新机制，是 `stree` 实现零延迟交互的核心支柱。

### 4.3 缓存与防抖

View 组件内置了 `cached_entity_id` 机制。当用户在树中移动光标时，如果新选中的节点 ID 与缓存一致，引擎**跳过命令执行**，直接复用内存中的 `content_buffer`。

这使得在万级节点的树中快速按 `j`/`k` 滚动时，不会触发任何 `fork()`，实现了真正的零 I/O 滚动。

## 5. 布局引擎：从特判黑魔法到纯正交 Flexbox

### 5.1 早期的黑魔法

在 V1.0 中，状态栏的处理方式是：如果窗口的 `border == None`，引擎会猜测它是状态栏，并将其高度强制截断为 1 行，在垂直布局中将其从百分比分配中剔除，最后硬塞到容器底部。

这段逻辑散布在 `compute_rects` 的多个位置，耦合了"边框样式"和"空间分配"两个本应正交的维度。

### 5.2 正交语法的引入

V2.0 引入了 `WindowSize` 枚举（`Percent(u16)` | `Absolute(u16)`），将尺寸声明与边框声明彻底分离。

*   `area(1)[none]:Status`：明确声明"绝对高度 1 行"和"无边框"。引擎不需要猜测。
*   `area(50%)[box]:Main`：明确声明"占 50% 空间"和"有边框"。

### 5.3 分配算法的边界处理

Flexbox 分配面临一个 TUI 特有的挑战：**整数除法余数**。

如果容器宽度为 100 字符，3 个节点各占 33%，则 `100 * 33 / 100 = 33`，3 个节点共占 99 字符，剩余 1 字符形成黑色缝隙。

引擎的策略是：将余数兜底加到最后一个有效的 flex 节点上。这确保了容器总是被精确填满，消除了 TUI 布局中最难看的视觉瑕疵。

## 6. 渲染管线：ANSI 透传与像素级截断

### 6.1 为什么不能简单截断

当一行文本超出窗口宽度时，简单的 `chars().take(width)` 会导致灾难：
*   如果截断点落在 ANSI 转义序列（如 `\x1b[31m`）中间，终端的颜色状态会崩溃，后续所有行的颜色都会错乱。
*   如果文本包含宽字符（如中文占 2 列），按字符数截断会导致实际显示宽度与预期不符。

### 6.2 分段解析

引擎的 `draw_text` 函数实现了 ANSI 感知的文本渲染：
1.  将文本拆分为 `Segment::Text`（纯文本）和 `Segment::Ansi`（转义序列）的交替序列。
2.  仅对 `Text` 段计算 `UnicodeWidthChar` 宽度。
3.  截断时，按可见字符宽度计数，确保不会劈裂 ANSI 序列。
4.  超出宽度时，在末尾追加 `~` 符号，并精确预留 1 个字符的宽度给 `~`。

## 7. 架构红线

以下原则是 `stree` 内核的宪法。任何违反这些原则的代码变更都将被视为架构退化。

### 7.1 绝不硬编码业务语义
引擎不理解什么是"文件"、什么是"笔记"、什么是"归档"。它只理解 ID、Display、Path 和 Tags。如果代码中出现了 `if status == "archived"` 这样的业务判断，那就是越界。

### 7.2 绝不持久化状态
引擎是无状态的纯函数映射。重启后，展开状态、选中状态、滚动偏移全部重置。持久化是业务层的责任。

### 7.3 提供机制，不提供策略
引擎提供标签匹配机制，但不定义标签的业务含义。引擎提供 IPC 通道，但不定义推送的内容格式。引擎提供占位符展开，但不定义命令的业务逻辑。

### 7.4 同步主循环的纯洁性
主循环（观测循环）的执行时间必须且只能消耗在纯计算上（渲染、事件处理、IPC 接收）。任何可能阻塞的物理操作（文件 I/O、网络请求、进程等待）都必须被剥离到子进程或后台线程中。

## 8. 性能边界与已知限制

| 场景 | 表现 | 原因 |
| :--- | :--- | :--- |
| 万级节点树滚动 | 丝滑（零 I/O） | `cached_entity_id` 防抖，内存缓存命中 |
| 鼠标滚轮连续滚动 | 单次 fork | `move_up_n` 批量移动，N 次位移仅触发 1 次广播 |
| `@` 静默模式瞬间切换 | < 5ms | 无 TTY 交接，无 Alternate Screen 切换 |
| `@` 模式下的耗时后台任务 | 不阻塞 UI | `.status()` + `Stdio::null()` 切断管道继承 |
| 搜索过滤 | 内存级实时 | `match_entities` 遍历 `Vec<Entity>`，无 I/O |
| IPC 局部刷新 | 单次重绘 | 仅更新目标组件，其他组件完全不受影响 |

### 已知限制
*   **单线程同步**：`broadcast_selection_changed` 中执行 View 命令是同步阻塞的。如果预览命令耗时较长（如渲染大型 PDF），UI 会短暂卡顿。缓解方案：业务层使用轻量级预览命令，或在脚本内部实现异步缓存。
*   **全量重建**：`trigger_reload`（SIGUSR1）会重新执行所有 Tree 的数据源命令。对于超大数据集，建议使用 IPC 定向更新替代全局重载。
*   **无增量 diff**：IPC 推送 Tree 数据时，引擎会重建整棵树的内存结构。对于频繁的小规模更新，这可能带来不必要的 CPU 开销。
