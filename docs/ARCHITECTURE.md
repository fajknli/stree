# stree 架构哲学与内核设计 (V3.0)

> 本文档记录 `stree` 引擎的核心设计决策、架构约束，以及每一个关键技术选择背后的工程推演。面向源码阅读者、贡献者，以及所有对 TUI 引擎底层机制感兴趣的人。

---

## 1. 范式声明：混合保留模式与声明式配置

### 1.1 为什么不是纯 Immediate Mode

主流 TUI 框架（Ratatui、Bubble Tea）采用完整的 **Retained Mode**，开发者构建组件树，框架持有所有状态。而早期 `stree` 曾尝试纯 **Immediate Mode + 外部状态**，即引擎不持有任何状态，每帧从外部数据源纯函数式投影。

实践证明，在终端环境中，纯 Immediate Mode 是不可行的：如果每次按 `j` 键移动光标，都需要外部脚本重新生成 TSV 并通过 IPC 推送，终端 IO 的延迟将彻底破坏 60fps 的交互体验。

### 1.2 混合状态模型

`stree` 最终确立了 **Retained UI State + Declarative Config** 的混合范式：
*   **高频交互状态（内部保留）**：焦点、展开节点、选中游标、标记集合、拖拽坐标、输入缓冲。这些状态由引擎通过 Rust 严格管理，确保零延迟响应。
*   **业务数据状态（外部注入）**：数据集内容、文件树结构作为不可变快照由外部脚本提供，通过 stdin/IPC 驱动更新。
*   **布局与组件装配（声明式）**：引擎启动时解析配置并构建 AST，运行时支持动态手术重组。

`stree` 不是一个单纯的渲染器，而是一个具备严格边界的 TUI 应用底座。

### 1.3 为什么纯 Rust 手写，不依赖 TUI 库

`stree` 的渲染层直接基于 `crossterm` 的原语，没有使用任何高级 TUI 组件库。原因有三：
1.  **像素级控制**：TUI 的布局精度要求极高。一个字符的溢出就会导致终端换行，换行会导致布局坍塌。
2.  **零抽象成本**：主循环是单线程同步的，没有任何异步运行时开销。每一帧的渲染路径是确定的、可预测的。
3.  **ANSI 透传**：引擎需要完美透传外部命令输出的 ANSI 转义序列，同时精准计算可见字符宽度。这要求渲染器必须理解 ANSI 的内部结构。

## 2. 协议驱动：Unix 管道哲学的极端化

### 2.1 四列 TSV 协议的设计动机

*   **TSV（制表符分隔）**：制表符在自然文本中几乎不会出现，无需转义。相比 CSV，解析成本低一个数量级，且完美兼容 `awk`、`cut` 等 Unix 标准工具。
*   **4 列的最小完备性**：
    *   第 1 列（ID）：图论必需的主键。
    *   第 2 列（Display）：人类可读的展示文本。
    *   第 3 列（Path）：机器可操作的业务负载。
    *   第 4 列（Tags）：多维度分类与样式映射的统一载体。

少于 4 列无法表达完整的树形交互语义；多于 4 列则意味着引擎开始理解业务语义，违背了"零业务侵入"原则。

### 2.2 Display 与 Path 的正交分离

*   `Display` 是给人看的。它可以包含格式化信息甚至 ANSI 颜色码。引擎只负责渲染，不解析。
*   `Path` 是给机器用的。它是外部命令的参数。引擎绝不打开它或解释它。

### 2.3 第四列的演化：从 Status 到 Tags

早期第四列名为 `status`，是单一值。为了同时表达"类型"和"状态"而不破坏协议，第四列演化为逗号分隔的标签集（如 `archived,note,inbox`）。样式引擎从"全等匹配"升级为"包含匹配"，在不改变物理结构的前提下，将表达能力提升到了 N 维。

## 3. 执行模型：双轨制与死锁防御

### 3.1 双轨制执行模型

TUI 引擎面临一个根本矛盾：终端只有一个，但引擎和外部命令都想拥有它。`stree` 提供两种执行轨道：
*   **默认模式（挂起 TUI）**：让出 Alternate Screen 和 TTY。适用于全屏交互工具（如 `vim`）。
*   **`@` 静默模式（保留 TUI）**：不交接 TTY，在后台执行。适用于纯状态变更（如归档文件）。

### 3.2 `@` 模式下的 fd 继承死锁

这是系统级陷阱。如果 `stree` 在静默模式下使用 `.output()` 执行 `sh -c 'long_task &'`，Rust 会创建 pipe 连接子进程。`long_task` 作为孙进程会继承 pipe 写端。`sh` 退出后，`long_task` 仍持有写端，导致 Rust 的 `.output()` 永远等不到 EOF，引擎主线程死锁。

**防御方案**：静默模式下，将 stdin/stdout/stderr 全部重定向到 `/dev/null`，并使用 `.status()` 替代 `.output()`。`.status()` 只调用 `waitpid()`，不读取管道，彻底切断继承链。

### 3.3 IPC 死锁的另一面

当 `@` 模式的脚本内部调用 `stree update` 时，同步调用会死锁（主线程等脚本退出，脚本等主线程处理 IPC）。
**契约**：业务层必须将 IPC 调用放入后台（`(...) &`），让脚本瞬间退出。引擎在下一轮 poll 中处理 IPC 请求。

## 4. 局部刷新与异步视图管线

### 4.1 IPC 定向刷新机制

`stree update <window_name>` 将刷新粒度从"全局"降维到"组件级"。
*   **Tree 组件**：接收新 TSV，增量更新 Dataset，保留展开/选中状态，仅重绘该树。
*   **View 组件**：直接替换内容缓冲区，仅重绘该预览窗口。

其他组件完全不受影响，实现了"指哪打哪"的零延迟交互。

### 4.2 异步 View 管线与防抖

View 组件内置了 `cached_entity_id` 机制。移动光标时，若新选中 ID 与缓存一致，引擎跳过命令执行，实现万级节点零 I/O 滚动。

对于未命中缓存的预览命令，`stree` 采用**异步线程池**模型：通过 `std::thread::spawn` 在后台执行命令，利用 `mpsc::channel` 将结果传回主线程。主线程在事件循环中非阻塞地 `try_recv`，只有当结果对应于当前最新选中 ID 时，才更新缓冲区。这彻底消除了预览大文件时的 UI 卡顿。

## 5. 布局引擎：正交 Flexbox 与 AST 动态手术

### 5.1 正交语法的引入

`WindowSize` 枚举（`Percent` | `Absolute` | `Absolute2D`）将尺寸声明与边框声明彻底分离。引擎不需要猜测窗口用途，一切由 `area(1)[none]:Status` 这样的语法明确声明。

### 5.2 AST 动态手术

这是 `stree` 布局引擎最硬核的魔法。当用户拖拽 Flexbox 分割线时，引擎不仅在物理上改变窗口大小，更会在运行时**重组布局 AST（抽象语法树）**：
1.  **树旋转**：将嵌套的叶子节点拉平为兄弟节点，改变拓扑结构。
2.  **像素反算**：用拖拽时的旧物理坐标，反算出新 AST 节点的百分比，杜绝拓扑突变带来的视觉跳跃。
3.  **覆盖注入**：拖拽过程中注入 `Absolute` 尺寸覆盖，松手时清除覆盖，让新 AST 百分比自然接管。

## 6. 渲染管线：零分配 ANSI 流式解析

### 6.1 为什么不能简单截断

简单按字符数截断会导致灾难：若截断点落在 ANSI 转义序列中间，终端颜色状态会崩溃；若包含宽字符（如中文），按字符截断会导致对齐错乱。

### 6.2 零分配流式解析

引擎的 `draw_clipped_text` 没有预生成 Segment 数组，而是实现了零分配的流式解析：
1.  通过 `char_indices().peekable()` 遍历字符串。
2.  遇到 `\x1b`，直接原地调用 `parse_ansi_sgr` 消费转义序列，更新当前颜色状态。
3.  仅对可见文本计算 `UnicodeWidthChar` 宽度，超宽时追加 `~`。

这保证了渲染层在高频重绘时的极致性能。

## 7. 统一执行上下文

### 7.1 从硬编码到 Context Map

早期 `stree` 的参数替换函数接受 8 个硬编码参数。为了支持 `{input}` 等动态变量，引擎引入了 `HashMap<String, String>` 作为统一的执行上下文（`ExecutionContext`）。

### 7.2 空格安全与确定性替换

*   **Split-Before-Replace**：`split_args` 发生在替换之前，无论业务变量（如 `{input}`）包含多少空格，都会被安全地视为单个参数，彻底杜绝参数截断 Bug。
*   **排序替换**：在遍历 Context Map 进行替换前，先对 Keys 排序。这确保了嵌套占位符（如 `{path}` 中包含 `{id}`）的替换顺序是确定性的，消除了 HashMap 迭代顺序不可控带来的潜在风险。

## 8. 架构红线

以下原则是 `stree` 内核的宪法。任何违反这些原则的代码变更都将被视为架构退化。

1.  **绝不硬编码业务语义**：引擎不理解"文件"或"归档"。只理解 ID、Display、Path 和 Tags。
2.  **易失状态原则**：引擎在内存中严格管理 UI 状态，但**绝不持久化到磁盘**。重启后状态重置。持久化是业务层的责任。
3.  **提供机制，不提供策略**：引擎提供标签匹配机制，但不定义标签含义。提供 `@` 静默机制，但不定义命令逻辑。
4.  **主循环纯洁性**：主循环的执行时间必须且只能消耗在纯计算上。任何可能阻塞的物理操作（文件 I/O、进程等待）必须被剥离到子进程或后台线程。

## 9. 性能边界与已知限制

| 场景 | 表现 | 原因 |
| :--- | :--- | :--- |
| 万级节点树滚动 | 丝滑（零 I/O） | `cached_entity_id` 防抖，内存缓存命中 |
| 鼠标滚轮连续滚动 | 单次 fork | `move_up_n` 批量移动，N 次位移仅触发 1 次广播 |
| `@` 静默模式瞬间切换 | < 5ms | 无 TTY 交接，无 Alternate Screen 切换 |
| 预览大文件 | UI 不卡顿 | View 命令丢入 `std::thread::spawn` 异步执行 |
| 拖拽窗口分割线 | 60fps | AST 重组 + Absolute 覆盖注入，无重排闪烁 |
| 搜索过滤 | 内存级实时 | `match_entities` 遍历 `Vec<Entity>`，无 I/O |

### 已知限制
*   **全量重建成本**：`trigger_reload`（SIGUSR1）会重新执行所有 Tree 的数据源命令。对于超大数据集，建议使用 IPC 定向更新替代全局重载。
*   **单线程 Diff**：渲染引擎的 Buffer Diff 是单线程同步的。在极端尺寸（如 4K 终端）下，全量重绘可能消耗数毫秒，但得益于增量 Diff，日常交互不受影响。
